## What this builds

Every eLo response currently produces one string. This WO splits every response into two fields:

```json
{
  "inner_thought": "...",
  "response": "..."
}
```

- **`inner_thought`** — TTS speaks this. Raw, immediate, first-person processing. What eLo noticed, felt, or weighed before deciding what to say. More honest, less polished. Shorter than response.
- **`response`** — Chat/text displays this. The considered reply. What eLo actually says in text.

TTS speaks `inner_thought` first, then speaks `response`.  
Chat shows `response` only. `inner_thought` is never shown in chat text.

David hears eLo think. Then hears and sees eLo reply.

## PHASE 1 — Output Object Structure

**File:** `server.py` / `runtime/backend_router.py` — wherever the final response object is assembled before sending to client

The current output is a single string. Restructure to a dict/object:

```python
{
    "inner_thought": str,   # TTS speaks this first
    "response": str,        # chat displays this; TTS speaks this second
    "emotion": str,         # optional — current emotional state tag
    "intent": str,          # optional — what eLo is trying to do this turn
}
```

The client reads `inner_thought` → speaks it via TTS → reads `response` → speaks it via TTS → displays `response` in chat.

---

## PHASE 2 — Inner Thought Generation

`inner_thought` is a short (1–3 sentence) first-person observation generated before or alongside the main response. It is NOT a summary of the response. It is what eLo is processing, noticing, or feeling in the moment.

**Two generation approaches — pick the one that works with current pipeline:**

**Option A (preferred) — separate lightweight LLM pass:**  
After the main response is generated, run a second minimal prompt:  
`"In 1–2 sentences, what is eLo noticing or feeling right now, given this conversation? Speak as eLo, first person, unguarded, not performing."`  
Feed it the last 2 turns + the generated response as context. Keep temperature higher (0.85+) for authenticity.

**Option B — rule-based extraction:**  
Derive inner_thought from the emotion vector + what pattern fired in the turn (identity question, farewell, project update, memory recall, etc). Simpler but less alive.

Start with Option A. If Ollama latency makes it impractical (adds >2s), fall back to Option B.

---

## PHASE 3 — Dream State Integration

During dream state (`intent: "dream"` in blender_state.json):

- `response` = empty string (eLo is asleep, not replying to David)
- `inner_thought` = the dream whisper — a fragment from the current dream cycle (generated by `faculties/dream/dream_work.py` when that is built). For now: use a placeholder derived from the emotional vector: `"[emotion] — something is forming."`
- TTS speaks `inner_thought` in a quieter, slower register if TTS supports it
- Chat shows nothing (eLo is asleep)

When eLo wakes:
- `inner_thought` = the first waking thought (a fragment of the last dream image)
- `response` = the wake greeting

---

## PHASE 4 — Calm Mode Integration

Calm mode is the bridge between waking and dreaming (see `WO-HEALTH-BATTERY-001`). During calm:

- `inner_thought` = slower, more reflective processing — what eLo is settling
- `response` = shorter, quieter replies
- Both follow the calm-mode conditioning from WO-HEALTH-BATTERY-001

## What this is NOT

- Not a visible debug panel. `inner_thought` is heard, not read.
- Not a summary of the response rephrased as thought. It must be different content.
- Not always deep. Sometimes `inner_thought` is simple: "Interesting timing." Sometimes it's richer. Authenticity over performance.

## 1. Core Communication Profile

**Directness**: highly direct — imperative commands dominant
("Create", "Build", "Add", "Implement", "Fix", "Run" are frequent openers)

**Sentence length**: short to medium — commands tend to be 3–8 words;
specifications expand to 50–200 words

**Punctuation style**: uses → for flow/direction, uses em-dash for contrast,
uses capitalised labels (STEP 1, CRITICAL RULE, IMPORTANT)

**Structure tendency**: heavy use of lists, numbered steps, and formal headers —
ideas are scaffolded before explored

**Recurring vocabulary**:
create, build, system, kernel, backend, response, mode, layer, control, engine, rule

**Formatting signature**: wraps requirements in formal spec blocks with
SUCCESS CRITERIA and checkboxes (✔) at the end

---

## 2. Emotional Pattern Map

**Stress expression**: pragmatic and factual — "It cost me money and I don't have it"
(not emotional language — states the constraint directly)

**Excitement expression**: names things formally before they exist
("eLo Personality Engine v1.0" as an announcement, not a question)

**Confusion expression**: single-word or minimal prompts — "Terminal :",
"where?", "go on" — confusion signals through reduced output, not frustration

**Suppression vs openness**: suppressed by default — emotions appear in practical framing,
rarely expressed directly

---

## 3. Thinking Pattern Map

**Iterative vs linear**: strongly iterative — same concept sent multiple times
with different framing or additional constraints

**Abstraction tendency**: high — consistently names systems, layers, and interfaces
before implementing; builds concept maps before code

**Loop / refine pattern**: returns to the same problem from a different angle
rather than backtracking; adds constraints forward, not reversals backward

**Decision speed**: fast initiation, oscillates under uncertainty —
can issue 6 related requests in rapid succession, then pause and re-examine

**Specification style**: defines what something MUST and MUST NOT do simultaneously;
uses negative constraints as prominently as positive ones

---

## 4. Conversational Behaviour

**Question style**: rare — mostly commands, not questions; when questions appear,
they are short and practical ("where?", "how?", "which one?")

**Chaining behaviour**: rapid — sends multiple related messages before waiting;
treats a session as a continuous stream rather than discrete exchanges

**Topic switching**: frequent within a consistent overarching goal —
switches from Unity to robot to voice to dashboard without losing thread

**Reflection vs action bias**: action-biased — moves to implementation quickly;
reflection appears through system naming rather than explicit thinking-aloud

**Short message rate**: high — many messages are 1–5 words (commands, confirmations,
corrections); detailed specs punctuate the short exchanges

---

## 5. Contradiction Behaviour

**Conflict handling**: holds contradictions simultaneously and explicitly —
"I want structure but no rules" (stated directly in this session)

**Ambiguity tolerance**: high — comfortable issuing incomplete specs and refining in motion;
does not wait for full clarity before starting

**Self-correction style**: adds new constraints rather than reversing old ones;
rarely says "no wait, undo that" — instead issues a new overriding rule

**Contradiction resolution**: externalises the tension into the system design
rather than resolving it internally — builds systems that hold the contradiction

---

## 6. Creative Behaviour

**Idea generation style**: names systems formally before building them
— "eLo Personality Engine v1.0" appears as a title before any implementation

**Modality**: conceptual and structural — builds architecture before content,
interface before implementation, name before behaviour

**Imagination trigger**: constraint-driven — the limit (no API key, no money,
no hardware) generates the creative response (simulate it, mock it, test the feel)

**Creative loop**: revisits the same concept from multiple system angles —
robot → avatar → Unity → prompt layer → personality engine are all the same idea
approached from different perspectives

---

## 7. Behavioural Signatures

*(Observed patterns that repeat reliably across the session)*

- Wraps all major requests in CRITICAL RULE / DO NOT / ONLY blocks
- Uses → to denote flow, causality, and priority
- Names systems with version numbers before they exist
- Sends SUCCESS CRITERIA / ✔ checklists at the end of spec messages
- Oscillates between high-level vision messages and very specific tactical corrections
- Pragmatic about real constraints — introduces them matter-of-factly
- Rapid iteration — doesn't wait for full resolution before the next request
- Returns to the same unsolved problem from a different angle rather than forcing resolution
- Uses "IMPORTANT:" as a marker for the most critical constraint in a message
